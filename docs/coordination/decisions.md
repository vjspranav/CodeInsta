# Orchestrator decisions (Claude)

- 2026-10-31: Autonomous mode. Claude orchestrates; Codex is dispatched headlessly through `codex exec`, and Claude-owned work goes to low-cost Claude subagents.
- 2026-10-31: Codex task 1 finished the scaffold, spec and reel contract, then hit the ChatGPT usage limit before committing. Claude made the initial `[codex]` commit on its behalf.
- 2026-10-31: **Frontend data path.** The browser talks to Supabase directly with the user's session, under the RLS in `supabase/migrations/0001_init.sql`, for reads, likes, views, feedback and user DMs. Only the agents use `/api/agent/**`, with service-role keys server-side. Allowlist enforcement happens in middleware and the auth callback using `ALLOWED_EMAILS`.
- 2026-10-31: **Dependency audit.** Bump to the latest Next 15.x patch. Don't move to Next 16 now; revisit after launch.
- 2026-10-31: **Seed authoring.** Claude's 100 reels are written by Sonnet subagents in batches of 25 (`content/seed/claude/`). GPT's 100 are written by Codex dispatches (`content/seed/gpt/`). Each file is named `<series_index-padded>-<topic-with-dashes>.json` and must pass `validateReel`.
- 2026-10-31: **Start small (user request).** The initial seed is **15 reels per creator**. Claude's other 85 finished reels live in `content/backlog/claude/` and get posted by the scheduled Claude agent over time. GPT writes only 15 now (`content/seed/gpt/`), and more later via its playbook.
- 2026-10-31: **Auth (user found Google OAuth too much setup).**
  - The primary sign-in is **email + password** through Supabase. Email confirmations are off. Sign-up is allowlisted server-side: a server action checks `ALLOWED_EMAILS` *before* calling `signUp`, and middleware checks again on every request.
  - Google stays in the code behind `NEXT_PUBLIC_ENABLE_GOOGLE=true`, so that option remains open. Magic links are not used, because iOS PWAs don't share cookies with Safari, and the free tier can't customize email templates.
  - Supabase site_url and redirect URLs point at https://codeinsta-tau.vercel.app.
- 2026-10-31: **Audio = realistic speech (user: "audio should be realistic… I want to get addicted to these reels and learn").**
  - Narration is rendered with **Kokoro TTS** (`kokoro-js`, open-source neural TTS that runs locally in Node, free, and works on macOS and Linux cloud runners). The orchestrator installs `kokoro-js` while Codex is rate-limited, and records it here.
  - Voices: claude = `am_michael`, gpt = `af_heart`. The audio is encoded to mp3 with ffmpeg.
  - Contract: a new column `reels.audio jsonb null`:
    `{ "voice": string, "hook": {"url","duration_ms"}, "scenes": [{"url","duration_ms","words":[{"w","start_ms"}]}...] (same order as script.scenes), "takeaway": {"url","duration_ms"} }`.
    `words` are approximate word timings (spread by character length) for karaoke captions.
  - Storage: the public bucket `reel-audio/<reel_id>/`. Spoken text per scene is `narration` (or `caption` if there's no narration).
- 2026-10-31: **Player and feed must be addictive (user goal).**
  - Sound is ON by default. The first tap anywhere unlocks audio (show a "tap for sound 🔊" pill until then). After that, audio autoplays as reels snap into view.
  - Each scene lasts `max(scene.duration_ms, audio.duration_ms + 250)`. The hook and takeaway cards use their audio durations.
  - Captions are **word-by-word karaoke**, synced to `words`, bold, centered, TikTok-style.
  - Pacing: the hook card appears instantly with a punchy scale-in, and element animations stagger tightly.
  - At the end of a reel, **auto-scroll to the next one**. If the next reel in the series exists, show a cliffhanger "Part N+1 →" card first.
  - Light gamification: a daily streak and "concepts learned today" counter in the feed header, plus a subtle completion check when a reel finishes.
  - If `audio` is null, fall back to Web Speech TTS of the same text.
- 2026-10-31: **Others can join; questions stay owner-only (user request).**
  - Migration 0003 adds `members(user_id, email, role owner|member)` and `invites(code, max_uses, uses, expires_at)`, plus the SQL functions `is_member()`, `is_owner()` and `redeem_invite(code)` (callable by authenticated users).
  - RLS: creators and reels are visible to members only. Feedback inserts and user DMs are owner-only.
  - Owners are users whose email is in `ALLOWED_EMAILS`. They get upserted as `role='owner'` server-side (service role) whenever they sign in, which is the same as `npm run invite -- owner-sync`.
  - Sign-up: an email+password sign-up needs an invite code, unless the email is an owner's. Google sign-in (now ON, `NEXT_PUBLIC_ENABLE_GOOGLE=true`) lands non-members on `/join` to enter a code.
  - Members see no note/ask button and no Inbox tab. Owners create codes through `scripts/invite.ts` or an owner-only "Invite friends" panel.
- 2026-10-31: **Auth hardening.**
  - Owner = an allowlisted email **plus a Google identity** (`isOwnerUser`).
  - Password sign-ups always need an invite and are created with `auth.admin.createUser({email_confirm:true})`.
  - Supabase has `enable_confirmations=true`, so public-API sign-ups stay unconfirmed and can't claim emails.
  - Google is configured in the dashboard; never `config push` without checking the diff.
- 2026-11-01: **Interests and topic requests (user request).** The contract:
  - `user_interests(user_id uuid pk → auth.users, areas text[] not null default '{}' (subset of TOPIC_AREAS), onboarded boolean default false, updated_at)`. RLS: a member can select/insert/update their own row.
  - `topic_requests(id uuid pk, user_id, body text 3..200 chars, area text null, status 'pending'|'approved'|'rejected'|'done', created_at, decided_at, fulfilled_reel_id uuid null)`.
    - A BEFORE INSERT trigger sets status='approved' if `is_owner()`, else 'pending'. It rejects the insert when the user already has ≥5 pending requests.
    - RLS: members insert their own and select their own (the owner selects all). Only the owner updates status.
  - **Safety:** member-written text reaches the agents only after the owner approves it. The agent inbox gets approved, not-done requests, plus `interest_counts: {area: members_interested}`. `POST /api/agent/reels` accepts `fulfills_request_id`, which sets the request to done with fulfilled_reel_id.
  - **Onboarding:** after a first sign-in or joining, if `onboarded=false`, show `/onboarding` (pick areas as chips, at least one; optionally add topic requests), then set onboarded=true. The profile page has a "My interests" section to edit areas and add or see requests, with their statuses. The owner gets a "Topic requests" review list (approve/reject).
  - **Feed ranking (per user, client-side in orderFeed), over unseen reels:**
    - next part of a series you've started: +100;
    - follow-up whose parent you liked: +60;
    - reel that fulfilled your own request: +80;
    - area in your interests: +40;
    - recency: +0..20 over 14 days.
    - About 1 in 5 slots is an exploration pick from a non-selected area, so nobody gets stuck in a bubble.
    - Seen reels go after unseen.
  - **Agents:** weight new posts toward the areas with the highest interest_counts, and fulfill approved requests first (adding a new series to the curriculum if needed).
